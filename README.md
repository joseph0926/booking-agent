# booking-agent

동네 가게의 예약을 받는 서버와, 그 위에서 손님과 대화하며 예약을 처리하는 상담 에이전트다. 예약 서버에서 시작해 LLM 상담원, 실시간 대화와 장애 대응까지 6주 동안 키운다.

이 저장소는 [서버와 AI 애플리케이션 트랙](../study/engineering/tracks/backend-ai/README.md)의 학습 프로젝트다. 주차별 목표와 진행 방식은 트랙 문서가 소유하고, 이 문서는 제품 설명과 API 계약을 소유한다. 단계별 작성 안내와 학습 진행 기록은 이 문서에 쓰지 않고 study 저장소의 학습 로그에 둔다.

## 제품

- 손님은 가게의 시간대(슬롯)를 골라 예약하고, 예약을 바꾸거나 취소한다.
- 3주차부터는 손님이 대화로 요청하면 상담 에이전트가 예약 API를 도구로 호출해 처리한다.
- 5주차부터는 가게마다 다른 정책(예약 가능 시간, 취소 마감, 사람에게 넘기는 조건)을 코드 수정 없이 설정으로 추가한다.

## 도메인 규칙 (1주차)

- 가게는 여러 슬롯을 가진다. 슬롯은 시작 시각으로 구분하며 길이는 60분이다.
- 한 슬롯에는 확정된 예약이 최대 1건이다.
- 예약의 상태는 `confirmed`와 `cancelled` 중 하나다. 취소된 예약은 슬롯을 차지하지 않는다.
- 예약 변경은 기존 슬롯을 비우고 새 슬롯을 차지하는 하나의 동작이다. 새 슬롯을 차지하지 못하면 기존 예약은 그대로 남는다.

## API 계약 (1주차)

예약 생성 요청의 `customerName`과 `slotStart`는 필수 문자열이다. 필드가 없거나, 문자열이 아니거나, 양끝 공백을 제거했을 때 빈 값이면 400을 반환한다.

`slotStart`는 `YYYY-MM-DDTHH:mm:ss` 뒤에 선택적인 세 자리 밀리초(`.sss`)와 필수 시차 표기를 붙인 형식으로 받는다. 날짜와 시각 사이에는 대문자 `T`를 쓰며, 시차는 대문자 `Z` 또는 `±HH:mm`로 표시한다. 밀리초는 어느 시차 표기에서든 생략할 수 있다. 다음은 허용 형식의 예다.

- `2026-11-10T18:00:00+09:00`
- `2026-11-10T09:00:00Z`
- `2026-11-10T09:00:00.123Z`
- `2026-11-10T18:00:00.123+09:00`

형식에 맞지 않거나 유효한 날짜와 시각이 아니면 400을 반환한다. 달력에 없는 날짜를 다른 날짜로 보정해 받아들이지 않는다. 저장 값과 응답의 `slotStart`는 UTC의 `YYYY-MM-DDTHH:mm:ss.sssZ` 형식으로 통일한다.

| 메서드와 경로 | 요청 | 성공 | 실패 |
|---|---|---|---|
| `POST /stores/:storeId/reservations` | `{ "slotStart": "2026-11-10T18:00:00+09:00", "customerName": "..." }` | `201` 예약 `{ id, storeId, slotStart, customerName, status }` | `409` 슬롯이 이미 찼음, `400` 잘못된 입력, `404` 없는 가게 |
| `PATCH /reservations/:id` | `{ "slotStart": "..." }` | `200` 바뀐 예약 | `409` 새 슬롯이 찼거나 이미 취소된 예약, `404` 없는 예약 |
| `DELETE /reservations/:id` | 없음 | `200` 취소된 예약 | `409` 이미 취소된 예약, `404` 없는 예약 |
| `GET /stores/:storeId/reservations?date=2026-11-10` | 없음 | `200` 그날의 확정된 예약 목록 | `400` 잘못된 날짜, `404` 없는 가게 |

목록 조회의 `date`는 한국 시간(UTC+09:00)의 날짜다. 그날 00:00 이상부터 다음 날 00:00 미만에 시작하는 확정 예약을 조회한다. 저장 값과 응답의 `slotStart`는 UTC 형식을 사용한다.

## 1주차 완료 조건

- 같은 슬롯에 동시에 들어온 예약 요청 20건 중 정확히 1건이 `201`, 나머지는 `409`다. 저장된 확정 예약도 1건이다.
- 같은 예약에 변경과 취소가 동시에 들어와도, 끝난 뒤의 저장 상태가 도메인 규칙을 어기지 않는다.
- 위 두 조건은 Vitest 테스트로 확인한다. 테스트는 사용자가 구현보다 먼저 쓴다.
- 한 프로세스의 동기 SQLite에서는 요청이 저절로 끼어들지 않으므로, 테스트는 조회와 저장 사이에 대기를 넣어 두 요청이 같은 상태를 읽은 뒤 쓰도록 순서를 제어한다. 응답 코드와 함께 저장된 최종 상태를 확인한다.

## 실행 환경

- Node 24, pnpm 12, TypeScript 7, NestJS 12, Vitest 5, SQLite(Node 내장 `node:sqlite`).
- Vitest는 NestJS 의존성 주입에 필요한 데코레이터 메타데이터를 만들기 위해 `unplugin-swc`로 변환한다.
- DB는 기본으로 메모리에서 열린다. 파일로 남기려면 `DB_PATH`를 지정한다(`data/`는 Git에서 제외).
- Git 저장소 생성과 커밋은 사용자가 한다.

```bash
pnpm install
```

```bash
pnpm test
```

```bash
pnpm build && pnpm start
```

## 구현 상태

- 예약 생성(`POST /stores/:storeId/reservations`): 없는 가게의 404, 두 필드의 기본 입력 검사, 날짜 변환 실패와 시차 표기 누락 및 달력에 없는 날짜의 400 처리가 있다. UTC 변환과 예약 저장 후 201을 반환한다. 슬롯 중복 제약 위반은 409로 응답하고 다른 DB 오류는 다시 던진다. 상세 입력 형식 검사는 일부 구현 상태로 후속 보완을 남겼다.
- 저장 구조: [schema.ts](./src/database/schema.ts)의 가게와 예약 테이블, 확정 예약에만 적용하는 부분 유니크 인덱스. 앱 시작 때 실행한다.
- 테스트: [reservations.e2e.test.ts](./test/reservations.e2e.test.ts)의 UTC 저장, 서로 다른 시간대 예약 생성, 달력에 없는 날짜 거절 테스트 3건은 사용자 실행으로 통과했다. 동시 예약 20건의 201 응답 1건과 409 응답 19건도 사용자 실행으로 확인했다. 최종 DB 확정 예약 수와 현재 전체 테스트 결과는 미확인이다. 상태 확인 테스트는 [health.e2e.test.ts](./test/health.e2e.test.ts)에 있다.
- 3주차부터 쓰는 모델 API 키는 사용자가 `.env`에 넣는다. 테스트는 모의 모델로 돌린다.
